| Next | Race time predictions (transparent) | Predict race times (for example 5K, 10K, half marathon, marathon) from the athlete's **real** performance, with every step visible. **Core requirement: no black box.** The app exists to give people open tools to plan with, rooted in good science, so each prediction must come with a "show your working" view: (1) *inputs*: exactly which efforts were used (activity, date, distance, time, conditions such as elevation, treadmill vs outdoor, temperature), why they qualified, and a toggle to exclude any of them and watch the prediction change; (2) *method*: the formula written out with the athlete's numbers substituted, the parameters it fitted (for example a personal pace-decay exponent instead of the textbook 1.06) and how; (3) *comparison*: several established methods side by side (the Riegel power law as the baseline, a critical-speed model, and a VDOT-style table) so disagreement is visible rather than hidden; (4) *uncertainty*: a range, not a single number, with how it was derived and a plain statement of how much data it rests on; (5) *back-test*: predictions made from earlier efforts checked against the athlete's actual later races, with the error reported; (6) *why it changed*: when a prediction moves, say which new effort caused it; (7) *sources*: links to the papers or documentation behind each method and its known limits; (8) *exportable*: the whole calculation as plain text or JSON so anyone can reproduce it. **Data:** Garmin's activity list already carries best splits (fastest 1 km, 1 mile, 5 km, 10 km and half marathon per activity), and the per-second samples allow finding the best effort at any distance. **What the evidence says (to design around):** the Riegel formula is T2 = T1 x (D2/D1)^1.06, but analysis of 1,071 experienced marathoners found fewer than 5% matched its predictions and most were slower, with an effective exponent nearer 1.15 ([Fetch Everyone analysis](https://www.fetcheveryone.com/article/marathon-time-prediction-37), a site analysis not a peer-reviewed study); an observational look at Garmin's predictor in a small group found a median implied exponent of about 1.13 ([Gneta case series](https://www.gneta.app/research/garmin-race-predictor), also not peer reviewed); a 2025 study of half-marathon-to-marathon prediction found its equation about as accurate as the VDOT system but behaving differently by runner level ([Valencia Marathon study](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC12856576/)); and a modelling paper reports VDOT-style predictions imply better endurance than some runners have, with marathon paces up to about 15 s/km slower in its comparison ([minimal power model](https://arxiv.org/pdf/1807.10595)). Figures are from abstracts and search summaries, not full texts, so the first build must re-read the primary sources before relying on them. Expect predictions to be least reliable for distances much longer than the efforts they come from, and to need training-load context (weekly mileage, longest run) for the marathon. Predictions are estimates for planning, not promises or medical advice. |
| Next | Automatic max heart rate and zones | Predict the athlete's max heart rate and calculate their zones from their own data, instead of asking them to type it in. **Plan:** (1) prefer Garmin's own zones once they are read from the heart-rate-zones data already being collected; (2) otherwise estimate from the user's data: take the highest *sustained* heart rate (for example a 30-second rolling average, with optical-sensor spikes and implausible jumps filtered out) across hard efforts in the last 1 to 2 years, use a robust summary of several efforts rather than one peak, and show how many efforts support it; (3) with too little data, fall back to an age formula once a date of birth is entered (Tanaka, 208 minus 0.7 x age, rather than 220 minus age); (4) a manual override always wins. Keep a dated history because max heart rate and zones change over time, treat running and cycling separately (cycling peaks are often lower), and label where every number came from (Garmin, your data, age formula, manual). **Why not just a formula:** age-based equations have individual errors of roughly 7 to 12 bpm; a 2023 study of 5,069 endurance athletes tested against lab maximal tests found most of the 13 running and cycling equations differed significantly from measured values (RMSE 9.1 to 10.5 bpm) and recommended using them only to supplement testing ([Kasiak et al., J Clin Med 2023](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC10146295/)); an exploratory study of 4,375 endurance athletes found age formulas systematically underestimate field-observed maximum heart rate ([field-based vs laboratory study](https://sponet.de/sponet/Record/4097777)); a HERITAGE Family Study comparison reported standard errors of about 11 to 12 bpm for the Tanaka and 220-minus-age formulas ([HERITAGE study](https://profiles.wustl.edu/en/publications/measured-maximal-heart-rates-compared-to-commonly-used-age-based-/)). Figures are from abstracts and search summaries, not the full texts. Caveats to design for: wrist optical heart rate misreads and spikes, and this is an estimate for training zones, not a medical test. |

## Decided so far

- **Open and explainable by design (core intent):** every number the app shows should say where it came from and how it was calculated, and plans should rest on cited science. Predictions and recommendations must "show their working"; see the race-prediction item.
- **Stack (approved 2026-11-01):** Python + FastAPI backend; React + TypeScript (Vite) single-page app, built into the same Docker image (multi-stage build, Node only at build time); SQLite (WAL mode); two image tags planned: `slim` (sync, dashboard, agent access; the only one built so far) and `full` (adds ingest converters: Docling, etc., CPU-only PyTorch; arrives with literature ingest). Chart and map libraries (e.g. uPlot/ECharts, MapLibre/Leaflet) to be chosen at v0.2, with a license check.
- Single container; SQLite-class embedded storage; runs on a small box (Intel N100, 16 GB) and portable to a cloud host.
- The Garmin API key is entered by the user in the running app's settings page (no env var, never shared with the developer or an AI). Needs the admin login from v0.1. Development and tests use recorded fixtures, not a real key.
- Garmin API key is encrypted at rest with a master key generated on first run and stored separately from the database (owner-only permissions); an optional environment variable or Docker secret overrides it (use this on a cloud host).
- MVP targets desktop. Single admin user with built-in login (safe if later exposed publicly).
- Mobile site, then installable web app, then multi-user, in that order.

## Backup design notes (for v0.2.1 / v0.2.2)

- Use SQLite's online backup, not a file copy, so a snapshot is consistent while syncing.
- The activity ZIPs are the original Garmin files, so they are also the safest long-term copy; they can be incrementally synced rather than re-archived each time.
- The master key stays out of ordinary backups (a backup containing both the database and its key defeats the encryption). Portable option: passphrase-encrypted archive.
- SMB credentials get the same encryption-at-rest as the Garmin key. Verify the share is reachable and writable when saving settings, and report backup failures in the UI.
