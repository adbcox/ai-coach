| Next | VO2max predictions (transparent) | **First version built (v0.4.0).** Two methods side by side with their working and ranges: race-performance VDOT (clearly labelled a performance index, not a measured VO2max) and the heart rate ratio method (15.3 x max HR / resting HR, +/- the paper's 4.7 ml/kg/min error, flagged as likely to read high), plus a field for the watch's own value to compare and a trend of your best VDOT over the last year. Garmin's Personal API does not expose VO2max. **Honest status of the evidence (v0.4.2, papers read in full):** both methods rest on older research (VDOT 1979, heart rate ratio 2004). Newer work read in full: the 2022 INTERLIVE meta-analysis (exercise-based wearable algorithms beat resting-data ones; resting-data ones read about 2.2 ml/kg/min high with individual differences of roughly -13 to +17); Wiecha et al. 2023 in PLOS ONE (13 published VO2max equations transfer poorly to 5,260 endurance athletes); Wiecha et al. 2023 in eLife (accurate, RMSE about 2 ml/kg/min, but every strong model needs laboratory gas-exchange data, and it covers men only); and Hata et al. 2025 (HYPAC, a GPS speed-and-slope oxygen-cost equation built on Minetti's slope data, validated on only 10 students). No recent, peer-reviewed method that runs from watch data alone and is validated in athletes has been found, so the submaximal heart-rate-versus-speed method stays on hold. An ACSM-in-athletes study mentioned earlier has not been read. **Still to do:** the submaximal heart-rate-versus-speed method (it needs a running-cost equation validated in athletes; HYPAC is the candidate but needs larger validation), and a rolling trend chart. | Next | Race time predictions (transparent) | **Built (v0.3.0, extended in v0.4.0): 5K, 10K, half marathon and marathon, with grade-adjusted pace (Minetti et al. 2002, verified against the full text), treadmill and trail runs included by default (trail only with grade adjustment), and marked races used for the back-test.** Best efforts are found inside each run with a sliding window over the per-second distance, then turned into predictions by five methods (Riegel k = 1.06, your own fitted exponent with a 95% prediction interval, a critical-speed model, Daniels/Gilbert VDOT, and a conservative k = 1.15 scenario), with the formula written out with your numbers, a headline range (fastest to slowest counted method, middle = median), a support rating, a back-test against your own earlier efforts, your recent training next to the half and marathon, a switch to leave any effort out, and the sources. Everything is also in the API and downloadable as JSON. **Original requirement, still the rule: no black box** (inputs, method, comparison, uncertainty, back-test, sources, exportable). **Still to do:** confirm against your real races (mark an activity as a race so the back-test uses real races instead of local bests), use Garmin's own splits as a cross-check, treat hilly runs with a grade adjustment, an explicit endurance adjustment for the marathon once there is evidence to cite, and re-read the primary papers (so far checked from abstracts and secondary summaries). Evidence behind the design: the Riegel formula is T2 = T1 x (D2/D1)^1.06, fitted to efforts of about 3.5 to 230 minutes ([Riegel 1981](https://en.wikipedia.org/wiki/Peter_Riegel)); an analysis of 1,071 experienced marathoners found fewer than 5% matched it, with an effective exponent nearer 1.15 ([Fetch Everyone](https://www.fetcheveryone.com/article/marathon-time-prediction-37), not peer reviewed); a 2025 study of half-marathon-to-marathon prediction found its equation about as accurate as the VDOT system but behaving differently by runner level ([Valencia Marathon study](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC12856576/)); the two-parameter critical power model is reviewed in [Poole et al. 2016](https://pmc.ncbi.nlm.nih.gov/articles/PMC5070974). |

## Decided so far

- **Mission:** use your data to train smarter, and always show the math. The user must be able to see how every number was made (where the inputs came from, the formula with their numbers, the uncertainty, and the sources).
- **Open and explainable by design (core intent):** every number the app shows should say where it came from and how it was calculated, and plans should rest on cited science. Predictions and recommendations must "show their working"; see the race-prediction item.
- **Stack (approved 2026-11-01):** Python + FastAPI backend; React + TypeScript (Vite) single-page app, built into the same Docker image (multi-stage build, Node only at build time); SQLite (WAL mode); two image tags planned: `slim` (sync, dashboard, agent access; the only one built so far) and `full` (adds ingest converters: Docling, etc., CPU-only PyTorch; arrives with literature ingest). Chart and map libraries (e.g. uPlot/ECharts, MapLibre/Leaflet) to be chosen at v0.2, with a license check.
- Single container; SQLite-class embedded storage; runs on a small box (Intel N100, 16 GB) and portable to a cloud host.
- The Garmin API key is entered by the user in the running app's settings page (no env var, never shared with the developer or an AI). Needs the admin login from v0.1. Development and tests use recorded fixtures, not a real key.
- Garmin API key is encrypted at rest with a master key generated on first run and stored separately from the database (owner-only permissions); an optional environment variable or Docker secret overrides it (use this on a cloud host).
- MVP targets desktop. Single admin user with built-in login (safe if later exposed publicly).
- Mobile site, then installable web app, then multi-user, in that order.

## Backup design notes (for v0.2.1 / v0.2.2)

- Use SQLite's online backup, not a file copy, so a snapshot is consistent while syncing.
- The activity ZIPs are the original Garmin files, so they are also the safest long-term copy; they can be incrementally synced rather than re-archived each time.
- The master key stays out of ordinary backups (a backup containing both the database and its key defeats the encryption). Portable option: passphrase-encrypted archive.
- SMB credentials get the same encryption-at-rest as the Garmin key. Verify the share is reachable and writable when saving settings, and report backup failures in the UI.
